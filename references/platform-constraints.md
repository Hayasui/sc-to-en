# UserTesting 平台限制与坑

面向 Unmoderated Test（无人主持）的配置限制。每条都是实际踩过或确认过的，改文档前先过一遍。

## 1. 字符数上限

| 字段 | 上限 | 说明 |
|------|------|------|
| Instruction text（Participant guidance） | **1000 字符** | 开场的说明文字 |
| Navigation task instructions | **1000 字符** | 导航任务的动作说明 |

**这条只约束这两个字段，不约束普通题干和选项。** 曾经误以为"所有题干都限 1000 字符"，
查证后确认：New experience 文档只写明 Participant guidance / Instructions 限 1000 字符，
普通 question text 与 answer option 的上限未公开（后台输入框宽松得多）。
所以题干里多写一两句邀请是安全的，不必为了凑字数把追问砍掉。

**对策**：把内容拆分到两个字段，各司其职，避免重复：

- **Instruction text** 只讲"玩家需要知道的原则"——试玩时长、边玩边说、自动录屏、怎么反馈 bug
- **Navigation task instructions** 只讲"下载并打开游戏"这一动作——点开链接 → 下载 → 打开 → 试玩

两者信息互补、不重叠，各自都能控制在 1000 字符内。中文的字符统计按字数算，英文按字符数算（英文更容易超限，注意核对）。

## 2. 自定义填写选项的标签限制

**平台只允许两种标签**：`Other` 或 `None of the above`。

**不能**写 `Other (please specify)`、`请说明`、`请填写名字`、`None of the above — but I played... (please name it)` 这类提示语。

**对策**：

- 选项直接写 `Other` / `None of the above`
- 如果确实需要知道"具体是什么"，**用后面一道 Verbal response 题去问**（玩家开口说，录音会记录），而不是在选项里塞提示
- 例：基准游戏题选了 `Other` → 下一道 Verbal 题里问"如果你选了 Other，请告诉我们你心里想的是哪款"

## 3. 条件逻辑：能力有限，且不要依赖

**平台的真实能力**（New experience 下的 Think-out-loud test）：

- **支持**条件跳转（Branching logic），但形式单一：只能做
  "If the answer is X → go to Question A, Otherwise → go to Question B" 这种**二分支**。
  多选题只允许**一条** multi-select 逻辑规则，评分量表规则可以多条。
- **不支持**把前一题的答案带进后一题的题干（Pipe answers）——那是 UserZoom 的功能，
  UserTesting 的 TOL 文档里没有。
- **不支持**组合条件（AND/OR 多条件判断）。

**判断：能用，但不该用。** 理由有三：

1. 样本量小（定性访谈常见 12-16 人），条件切分后每支只剩几个人，没有分析价值
2. 跳转配在后台，配错一次整批数据就废，且不易在测试前发现
3. 玩家不知道自己被跳过了什么，体验上容易困惑

**对策：需要"分两类人问不同问题"时，把两段分支写进同一道 Verbal 题的题干，让玩家自己认领。**
这是实际项目验证过的写法（参考案例：Balloon Carnival 活动参与题，题干里写
"如果有参与：……／如果没有参与：……"）。写法要点：

- 每段开头用**加粗的条件标签**（"如果你刚才选的是'没花过钱'——"），让玩家一眼找到自己那段
- 题干首句先交代"下面两段请按你自己的情况选一段来答"
- 注意：加粗在平台上可能失效，条件标签**去掉加粗后仍要能读出来**（如用"如果你……"这样的句式承载）

**其他相关限制**：

- 平台做不到"玩家在 Q10 选过的游戏，出现在 Q11 的选项里"这种条件逻辑
- 需要玩家记住前面选择、后面反复引用的（如"基准游戏"），**在题干里提示玩家自己记下来**（可以写纸上）

## 4. 量表题必须填 Scale Labels

所有 **Rating scale** 和 **Matrix** 题，配置时都要填两端的 **Scale Labels**。

**NPS 题型另办**：平台自带 0-10，标签可写可不写；写就照 `survey-wording.md`（低端 `0 = Not likely at all`，高端 `10 = Extremely likely`）。

**对策**：在文档里为每道量表题显式写出 Scale Labels。

**端点的具体措辞见 `survey-wording.md`——那份是唯一出处，不要在本文件里另抄一份。**
它列了项目在用的四套端点、固定选项标签、逐行出处，以及平台真实的结构限制
（Numeric 型量程 -3 到 10、Customized 型标签上限 7）。要加一套新端点，先改那份表。

判断端点是否贴题只有一条：**读端点就知道题在问什么**。满意度用 satisfied 系、
可能性用 play / likely 系、同意度用 agree 系，不要所有量表题都套同一组端点。

**区间要全篇统一（2026-09-15 起改为 1-7）**：同一份问卷里的 Rating scale 与 Matrix **一律 1-7**，
不要混用 0-10、1-10 和 1-5。理由两条：奇数点没有真正的中间"中立"位（4 是重心，
统计上不会把满意度压在正中间），以及贴 Likert 七级量表的主流写法。
**只有 NPS 例外**——它是行业标准量表，固定 0-10 不动。
（沿革：2026-09-09 定过"一律 1-10"，2026-09-15 按严谨性与统计有效性改定为 1-7，中英同步。）

## 5. Question Page 分页

一个 **Question Page** 可以放多道相关联的题，减少玩家翻页负担。

**注意：同一 Question Page 里的题目是"同屏/连续展示、全部答完才进入下一段"，不是逐题提交。**
（"逐题展示"的说法只在没有分页时成立；有了 Question Page，页内的题是一组。）

**官方推荐上限：每页不超过 10 道题。** 支持的题型：Multiple choice、Written response、
Rating scale、NPS、Matrix、Ranking、Image、Instructions。

**对策**：把同一主题的题放在同一页（如"设备背景"一页、"基准游戏"一页、"满意度打分"一页）。相关题放一起，玩家的思路也更连贯。

## 6. 加粗（bold）不可靠

**平台上可能无法设置粗体**。文档里保留 `**加粗**` 标记是为了便于人阅读，但**真正粘贴到平台时加粗会失效**。

**对策**：确保每句话**去掉加粗后依然读得通**。不要把关键信息只靠加粗来承载（比如不要写 "选 **①** 才算通过" 这种依赖加粗的表述）。

## 7. 题目编号要删除

平台是**逐题展示**的，文档里的 `Q1`、`题 3` 这类编号**上线时要删掉**（只作为内部沟通用）。

## 8. 无法设置"必答/选答"以外的复杂校验

平台只支持必答/选答。复杂的跳转逻辑、条件校验都做不到。

**对策**：把复杂逻辑前置到**甄别问卷的 Targeting criteria** 或后置到**人工复核**，不要指望访谈题里实现。

## 9. 题型清单（7 种）

Multiple Choice（单选/多选）、Written response、Rating scale、NPS、Matrix、Verbal response、Ranking。

**选型建议**：

- 定性探问 → **Verbal response**（玩家开口说，录音被记录；无人主持时这是最接近"追问"的形式）
- 多子维度一次评 → **Matrix**（比拆成多道单题更聚焦）
- 优先级排序 → **Ranking**
- 背景/档位/意愿 → **Multiple Choice**

## 10. 全程录音带来的额外自由度

Unmoderated Think-Out-Loud 测试**全程录音**。这意味着：即使玩家在填定量题（单选、量表），他的口头解释也会被录下来。

**对策**：在定量题的题干里主动邀请玩家"顺便说说为什么这么选"，补上无人主持时缺失的"临场追问"。

**分工要清楚**（2026-09-09 定案）：**内嵌邀请收事实，独立 Verbal 收动机。**

- 题干里的"顺便说说……"只收**具体的、一句话能答完的事实**（什么时候玩、最近一次买了什么）
- 需要展开的**动机 / 原因 / 跨场景对比**，另开一道 Verbal response 题
- 页面引导语负责下总指令（"其中有两道题会请你一边选一边顺口说说"），题干负责给具体追问点，两处不重复

反面做法：把动机类追问也塞进题干，题干变长、玩家只应一句就过，反而收不到深度。

## 11. 内嵌邀请排在题干里，不另立字段（2026-09-11）

**题干的输入框支持换行。** 所以那些想让玩家"边填定量题、边开口补充"的邀请句，
直接排在**题干文字的下方**，另起行、段间空一行，**不带 `**内嵌追问**：` 这类字段名**——
玩家不该看到给内部看的标签。

排法（英文侧示例）：

```
**Stem**: Over the past 1 month, roughly how much have you spent on merge games — ...?

If you chose "I didn't spend anything" — what kept you from spending? ...

If you did spend — which games were they, and what did you buy? ...

- I didn't spend anything
- $1-9
```

**分支题不加额外的引导句。** 不要写"请在下面两段里选一段"这类话：中文定稿里那句是
内部字段名的一部分，英文补一句就多出一段玩家可见文字，中英在"玩家可见内容"上就对不齐了。
`If you chose… / If you did spend…` 这样的条件开头本身已经说明该认领哪段。

**这批追问行不要加 `- ` 前缀**——选项也是 `- `，加了会让 lint 的选项计数与人工配置都分不清
哪些是选项。

**有人版的「追问方向」不适用本规则**：它是主持人现场用的，不进玩家可见题干，保持独立分栏。
