# sc-to-en

把用研的中文 Markdown 文档，本地化成能直接贴进 UserTesting 的英文版。

不是直译。用研文档有两种读者——玩家读题干和选项，研究团队读研究落点和内部备注。中文定稿写完之后，
还需要一份英文版配置到平台上。逐句直译会撞上两类问题。一类来自平台：字段有字符上限，自填选项
只能叫 `Other` 或 `None of the above`，选项无法按前一题的答案动态生成，量表题必须填 Scale Labels。
另一类来自语言本身：中式英文、玩家看不懂的行业术语、生硬的祈使句。

这个仓库把这两类问题拆成流程、检查清单和自动校验脚本，让每次本地化都走同一条路。

## 目录

```
SKILL.md                      主流程（场景判断 → 本地化 → 校验 → 汇报）
references/
  platform-constraints.md     UserTesting 平台限制与坑（含条件逻辑的真实能力）
  localization-principles.md  英文本地化标准（不直译、无俚语、面向普通玩家）
  doc-structure.md            文档结构规范（玩家可见/内部参考分离、有人/无人版命名）
  glossary.md                 术语对照表（跨文档、跨会话保持一致）
  checklist.md                交付前逐项检查清单
  roadmap.md                  升级路线图与已知未解决项
scripts/
  lint_usertesting.py         自动校验（中英对齐、题号、隐形字符、平台限制）
  test_lint.py                lint 的回归测试（26 个用例，正例+反例成对）
```

## 用法

校验一份英文稿：

```bash
python scripts/lint_usertesting.py <英文版.md>
```

同时比对中文稿，能查出中英对不上的地方，推荐这么做：

```bash
python scripts/lint_usertesting.py <英文版.md> --sc <中文版.md>
```

脚本检查这几类问题：

| 类别 | 内容 |
|------|------|
| 平台 | Instruction/Navigation 超 1000 字符、禁止的自填提示、量表题缺 Scale Labels |
| 本地化 | 残留汉字 / 中文标点 / 中文标点序号 / 隐形字符 |
| 结构 | 题号连续性与重复、题号交叉引用是否指向存在的题、Task/Page 或环节结构完整性 |
| 对齐 | 中英题号数、每题选项数、量表端点是否一致（需 `--sc`） |

改过 `lint_usertesting.py` 之后，跑一遍自测：

```bash
python scripts/test_lint.py
```

## 定下来的几条原则

中文稿是源头。内容设计在中文版定稿，它是内部审阅和与需求方沟通的基准。英文版是本地化产物，
面向玩家，措辞可以自由调整，但一旦动了语义，必须回写中文版。下游还有一层 xlsx 留档，
它只是渲染产物，不参与版本判定——中英不一致时报出来由人判断，不自行裁决。

只本地化玩家可见的部分。题干、选项、量表标签、页面引导语是给玩家看的，要重点打磨；
研究落点、内部备注、研究假设是给团队看的，保持原样。这一步最容易出错的地方，
是把内部备注也翻得花里胡哨，反而丢掉了团队需要的精确表述。

平台限制优先于语言美感。一句话再漂亮，违反平台字段限制也得改。先满足平台，再谈地道。

## 使用前提

Python 3.8 以上，没有第三方依赖，lint 和测试都只用标准库。面向 UserTesting 的
无人主持 Think-out-Loud Test 与有主持人访谈。

## 许可

内部研究工具，按需自取。
