# sc-to-en

本仓库把用研的中文 Markdown 文档适配为可直接配置到 UserTesting 的英文版。输入是中文定稿，输出是英文定稿与平台配置，供负责问卷与访谈上线的人使用。

这不是逐句直译的工作。用研文档有两种读者，玩家读题干与选项，研究团队读研究落点与内部备注，翻译时得把两类问题分开看。平台限制是一类：字段有字符上限，自填选项只能叫 `Other` 或 `None of the above`，选项无法按前一题的答案动态生成，Rating scale 与 Matrix 题要填两端的 Scale Labels，NPS 例外，它的标签可写可不写，写则低端从 0 起算。英文表达的质量问题是另一类：中式英文、玩家看不懂的行业术语、生硬的祈使句。

本仓库把这两类问题的处理固定成一套流程、几份检查清单和一个自动校验脚本，每次本地化都照此执行。

## 目录

```
SKILL.md                      主流程（场景判断 → 本地化 → 校验 → 汇报）
references/
  survey-wording.md           量表端点与固定选项标签的唯一出处（其余文件只写指针）
  platform-constraints.md     UserTesting 平台限制与坑（含条件逻辑的真实能力）
  localization-principles.md  英文本地化标准（不直译、无俚语、面向普通玩家）
  doc-structure.md            文档结构规范（玩家可见/内部参考分离、有人/无人版命名）
  glossary.md                 术语对照表（跨文档、跨会话保持一致）
  checklist.md                交付前逐项检查清单
  roadmap.md                  升级路线图与已知未解决项
scripts/
  lint_usertesting.py         自动校验（中英对齐、题号、隐形字符、平台限制）
  test_lint.py                lint 的回归测试（32 个用例，正例+反例成对）
```

## 用法

校验一份英文稿：

```bash
python scripts/lint_usertesting.py <英文版.md>
```

同时比对中文稿，能查出中英对不上的地方，推荐这么做：

```bash
python scripts/lint_usertesting.py <英文版.md> --sc <中文版.md>
```

脚本检查这几类问题：

| 类别 | 内容 |
|------|------|
| 平台 | Instruction/Navigation 超 1000 字符、禁止的自填提示、Rating scale 与 Matrix 题缺 Scale Labels、NPS 题写了标签但低端不是 0 |
| 本地化 | 残留汉字 / 中文标点 / 中文标点序号 / 隐形字符 |
| 结构 | 题号连续性与重复、题号交叉引用是否指向存在的题、Task/Page 或环节结构完整性 |
| 对齐 | 中英题号数、每题选项数、量表端点是否一致（需 `--sc`） |

改过 `lint_usertesting.py` 之后，跑一遍自测：

```bash
python scripts/test_lint.py
```

## 定下来的几条原则

中文稿是源头，内容在中文版定稿，它是内部审阅和与需求方沟通的基准。英文版是本地化产物，面向玩家，措辞可以自由调整，但一动语义就得回写中文版。下游还有一层 xlsx 留档，那只是渲染产物，不参与版本判定，中英不一致时报出来交给人判断，不自行裁决。

本地化只做玩家可见的部分。题干、选项、量表标签、页面引导语是给玩家看的，要重点打磨；研究落点、内部备注、研究假设是给团队看的，保持原样。这一步最容易出错的地方，是把内部备注也翻得花里胡哨，反倒丢掉了团队需要的精确表述。

平台限制优先于语言美感。一句话再漂亮，违反平台字段限制也得改。先满足平台，再谈地道。

## 使用前提

Python 3.8 以上，没有第三方依赖，lint 和测试都只用标准库。适用的场景是 UserTesting 上的无人主持 Think-out-Loud Test 与有主持人访谈。

## 许可

内部研究工具，按需自取。
